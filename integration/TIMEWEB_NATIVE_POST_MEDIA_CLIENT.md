# Native post media — source only, 2026-10-03

Feed/author walls/comments now render a post mediaId through GET /v1/runtime/posts/{postId}/media/{tw-post-media-64hex}/content. The request has native current-owner bearer, no query/body and no caller URL. JPEG/PNG/WebP HTTP200 requires exact bounded Content-Length 1..5 MiB and private no-store behavior; redirects/Location, public caching, compressed encoding, ranges, invalid MIME or size/stream mismatch are refused. HTTP404 is target-only unavailable with no healthy-account logout; HTTP401 uses the existing one-refresh/current-epoch behavior; verification503 shows an honest retry state.

New page-owned reader reuses existing _PeopleFlight cancellation/deadline/drain and the shared four actual request slots. Its byte attempt follows the strict existing profile-photo transport pattern; the original profile reader/HTTP helpers are unchanged. The current shared request deadline also bounds post media. Closing aborts only that reader's transfers and waits actual transport/stream drain, zeros owned bytes and retires DTOs. This drain expects the existing HTTP transport to honor AbortableRequest; an injected sender that ignores abort must eventually resolve before drain can complete. No new retry/queue framework was introduced.

The current runtime lease is bound before handing a reader to the image widget. Bytes stay in RAM, getters return copies, refresh retires previous byte generations, and logout/A→B invalidates the page/reader. The widget evicts its MemoryImage and clears its copied buffer on disposal/session invalidation. Feed refresh mounts a new image reader; it does not keep stale image capabilities. Failure uses the existing translated unavailable-photo message/manual retry, with no Firebase URL, fake image or disk cache.
