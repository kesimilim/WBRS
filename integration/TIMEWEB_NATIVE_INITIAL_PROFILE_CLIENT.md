# Native initial profile client — source contract

`TimewebAppRuntime.openInitialProfile()` restores only this native origin/UID draft. It makes no profile, photo, catalog or Firebase request. Normal UI entry requires the current blank canonical profile; a separate original-check entry may restore a pending finish even when current own-profile GET already reports saved=true. A restored pending finish permits only its original receipt lookup, with the owner/current auth epoch preserved; it does not repeat a POST or upload.

`TimewebInitialProfileFlow.readyPhotos` contains up to three retained historical pointers, not a fresh media capability. `runtime.openPhotoUpload(onReady: flow.addReadyPhoto)` awaits an idempotent, owner-guarded, flushed and read-back initial draft write **before** retiring the photo journal/commit reference. If that callback fails or the owner changes, photo READY is not published and the original photo intent remains available for lookup. The callback repeats safely after restart with the same media/prepare/commit UUIDs. Default photo upload callers without this callback retain their previous semantics. `checkPhotos()` freshly looks up all three original commits under the same native owner/budget; missing, short or mismatched proof refuses without deleting these pointers or logging out a healthy actor.

The typed request requires an exact current `expectedUpdatedAt`, all eight existing `TimewebProfileChanges` fields, pinned `TimewebGeographyChanges.fromCatalog(countryCode,region)`, and three distinct owner-bound `TimewebInitialPhotoProof` values. Original strings and pointer ordering are retained; nested JSON maps are explicitly typed to preserve the existing canonical hash. `submit(request)` rechecks all three original commits, durably retains the finish UUID/hash/exact fields before its single POST, and uses `profile.finish-registration.v1` at `/v1/runtime/me/registration`. Success is only the exact owner receipt `{uid,profileDetailsSaved:true,onboarding:test,updatedAt,profileAuthority:canonical-current-v1}`, entityRevision=null, after draft deletion/readback and client ACK. It marks details saved; it does not complete the questionnaire or registration.

Matching committed 404 errors are profile_not_found/photo_not_found; matching 409 errors are photo_not_ready and the timestamp-bearing profile_changed/registration_already_saved/registration_already_completed. All thin/nonreceipt errors, including healthy 403/404 or operation-not-found, remain UNKNOWN and cannot ACK. Original finish reconciliation never rechecks photos separately or posts an alternate UUID. Declared rejection retires the finish intent but preserves the three retained pointers; any later attempt needs an explicit fresh flow/request/current profile timestamp. Successful ACK clears the draft and RAM pointers; owner replacement/close clears RAM and preserves any pending disk record.

The bounded journal stores only origin, owner UID, 0..3 original pointers and optionally the exact finish request/UUID/hash (64KiB maximum). It contains no password/token/URL/header/photo bytes/local path. It uses the existing serialized temporary-flush/atomic-rename/CAS pattern in the OS application-support directory, plus exact write/readback and deletion readback. Private source artifacts are 0600; mobile journal isolation relies on the existing OS app sandbox, not an invented cross-platform chmod claim.

Four new focused scenario groups were checked. Three passed on the first module run; the finish/restart group found the nested-map canonical hash mismatch, repaired in the new request, and then passed after correcting its synchronous-throw test matcher. Only that affected group was rerun; old photo/meeting/profile modules were not run. Cases cover before-ACK callback failure/restart/idempotency, three exact retained proofs, no URL/binary draft, persist-before-POST, duplicate taps, lost ACK/not_found/original-only recovery, exact receipt/error/owner bindings, disk ACK, and late A→B result/drain. Scoped analysis found no production errors; new files/test finish with No issues found after style/null-assertion fixes. These are synthetic local tests, not actual SQL/S3/provider/auth acceptance. Runtime/public feature flags, permissions and production photo writer activation remain unchanged and default closed.
