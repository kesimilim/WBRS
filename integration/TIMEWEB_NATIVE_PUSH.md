# Native push: original ownership and bounded delivery

`runtime_push.py`, `runtime_push_http.py` and `native_fcm.py` add token registration independently of the provider. They reuse the current native session, shared `RuntimeMutationStore`, four transaction slots, existing runtime gates and `device_push_tokens`/`outbox` tables. They do not use Firebase customer identities or Firestore token storage. Missing/invalid `CLRS_NATIVE_PUSH_TOKEN_KEY_B64` (a separate persistent Base64 32-byte server key) closes registration; missing/invalid `CLRS_NATIVE_FCM_SERVICE_ACCOUNT_B64` closes delivery without claiming an outbox row. No credentials, bearer tokens, raw FCM tokens or message text enter replies or logs. The AES-GCM token envelope binds owner, device and exact native session; only its SHA256 remains indexed. Revocation updates a deterministic private tombstone and clears ciphertext; no token DELETE is needed. There are at most four stored device slots, with empty slots reusable.

The register route is `POST /v1/runtime/me/push-token/register`, exact body `{operationId,token}`, operation `push.register.v1`. Token is the unchanged ASCII 33..126 string of 20..4096 characters. The server derives the session ID, never accepts one in the body. The original request hash is SHA256 of UTF8 canonical JSON `{sessionId,tokenHash}`, with sorted keys, compact separators and `tokenHash=SHA256(UTF8 exact token)` as lowercase hex. A committed 200 result is exactly `{kind:'canonical-native-push',sessionId,registered:true}`, with null entity revision. Matching committed 409 errors are only `token_in_use` and `device_limit`. Revoke is `POST /v1/runtime/me/push-token/revoke`, exact body `{operationId}`, operation `push.revoke.v1`, request hash over `{sessionId}`; committed 200 is exactly `{kind:'canonical-native-push',sessionId,revoked:true}`, null entity revision and no declared rejection. Original lookup uses the existing operation/UUID/requestHash route. All short/nonreceipt errors remain UNKNOWN; they must not clear the original client intent. Native SID is canonical Base64url of 24 bytes (32 characters), not hex.

Receipts describe the original session, not present token registration. A current same-owner session may look up a historical original receipt after refresh/new login, but must not claim its old SID is currently registered. The client keeps raw FCM token only in RAM; its original durable record needs owner/origin/original SID, UUID and hashes. An automatic auth refresh must not POST an old original under the new SID. After historical confirmation, a new explicit current-SID intent may register the current RAM token. Active cross-owner/device token reuse is rejected, never transferred implicitly; atomic normal logout frees the physical token for another owner's new registration.

## Required narrow assembly hooks

Root owns existing assembly files. Create the HTTP adapter with `create_runtime_push_http(env, same_runtime_store)` and local-import it inside `runtime_http._create` to avoid circular imports. Append its dispatcher while preserving prior service tuple indices and preview/native-auth handling. Registration is gated only by the existing runtime WRITES/current-authority gates; there is no new public switch. Strict runtime grants need SELECT/INSERT/UPDATE on `device_push_tokens` and SELECT/INSERT/UPDATE on `outbox` in addition to existing grants. The currently approved provider database role remains honestly database-scoped, not a narrow-role claim.

Inject the same `PushCodec` into native session operations and call these hooks with their existing cursor/execute function **inside the original native auth transaction**, before its COMMIT:

- Normal one-session logout: `revoke_session_token(cursor, execute, codec, uid, deviceId, sid)`.
- All-session logout: `revoke_owner_tokens(cursor, execute, codec, uid)`.
- Refresh replay that revokes every session of one device: `revoke_owner_tokens(cursor, execute, codec, uid, deviceId)`.
- Successful refresh, after new-session INSERT: `rotate_session_token(cursor, execute, codec, uid, deviceId, oldSid, newSid)`.

The narrow auth table-grant model also needs token SELECT/UPDATE if hooks are enabled. The provider database permission model already permits these statements. Key loss/rotation is not silently accepted: unreadable active ciphertext fails closed. No token hook may run through another connection after auth COMMIT. Revoking an old SID must not erase a ciphertext already bound to its new refreshed SID.

Native chat already has a same-transaction outbox row. Gift send already emits the exact `chat.message.created.v1` event for its persisted gift notice; retain its returned event IDs and call `enqueue_event(cursor, execute, peerUid, events[1], eventKind, exactPayload)` when the current peer chat notifications flag allows it, only in the original action, never replay. Meeting send calls `enqueue_meeting_message(cursor, execute, exactPayload)` after the actual message/revision mutation. The helper selects at most 128 current non-left/non-kicked recipients and performs bounded bulk event/outbox INSERTs with counter CAS. Overflow refuses the original transaction rather than silently dropping recipients. Its exact payload is `{meetingId,messageId,sequence,senderUid,chatRevision,createdAt}`; original native/imported authorization stays with the existing domain action.

Construct `RuntimePushWorker(same_runtime_store, codec, create_native_fcm(env), imported_authority=genuine_authority)` only with the configured codec. Provider construction makes no HTTP requests. Start the worker explicitly in server lifecycle after accepted configuration; close it before closing the shared store. This source does not start a worker or activate runtime configuration by itself.

## Delivery and current access

Each run is one outbox row, at most four devices and an eight-second total deadline. The worker borrows the actual store's slots, TLS/configuration/grants checks and per-transaction 64-statement budget. It verifies the exact original `user_events` payload before committing `attempts=1`. Each attempted device then holds current token/session/account/preferences and domain access read locks through the FCM call: encrypted SID/token hash must still match, session must be unrevoked/unexpired and token version current, account must be active. Chat/gift uses current `messages`, peer notification flag and actual message; meeting uses current `meetings`, genuine native/imported membership authority and proved message. Sound follows current `sound`. No source text or arbitrary URL is passed to FCM. This is private member/chat access, not an invented public-search requirement.

FCM uses only a Google **service-account** credential for project `chatapp-4e347`, RS256 JWT and `firebase.messaging` scope. Operator Firebase CLI refresh credentials are refused. HTTPS hosts are fixed to `oauth2.googleapis.com` and `fcm.googleapis.com`, default CA/hostname verification, no redirects, <=16KiB replies, no automatic HTTP retry. Google documents the required [HTTP v1 service-account authorization](https://firebase.google.com/docs/cloud-messaging/send/v1-api) and [JWT service-account flow](https://developers.google.com/identity/protocols/oauth2/service-account). A decoded 200 FCM message-name response confirms provider acceptance, **not delivery to a device**. Notification text is generic; route IDs are data, with Android `wbrs` / `wbrs_silent` channels which the client must create.

The committed claim is terminal for retry selection even after timeout, crash or unknown COMMIT: only attempts=0 are selected; claimed rows move outside the ready index horizon. Full confirmation records `fcm.sent.v1`/`delivered_at`; ineligible devices are skipped, partial/uncertain acceptance records `fcm.partial_unknown.v1` or `fcm.unknown.v1` and never automatically resends. A crashed claimed row retains `fcm.sending.v1`, also no retry. No provider credential means no claim. Outbox/event payload and original operation receipt are not rewritten.
