# Native profile-photo mount

`app.py` wraps the existing imported-profile-photo HTTP factory only during application initialization after the operator preview guard. `create_native_profile_photos_http(env, legacy_http)` returns that exact legacy object when `CLRS_RUNTIME_NATIVE_PHOTO_UPLOADS_ENABLED` is absent or differs from `1`. When enabled, the reviewed composite owns and closes its native reader and the legacy HTTP resource; imported photo authority is not reclassified as native upload authority.

`RuntimeMutationHttp` appends upload dispatch at service tuple index 9; store/chat/profile/personal/meeting/initial indices 0–8 and the original initial-registration receipt lookup remain unchanged. Provider-database setup constructs one profile-photo SQL/proof core on the existing runtime store and shares it with initial registration and upload HTTP. Upload routes are not mounted when the new gate is off; with the gate on but no attested writer, they remain unavailable. Existing native bearer authorization and current-store checks are delegated to the unchanged upload HTTP/core. No fallback writer, imported read key, new SQL permission, activation, or second upload store is introduced.

The factory's separate explicit writer configuration and signed provider/release or pilot evidence are still required. Its source binding includes the new `app.py` and `runtime_http.py` bytes; an older source-bound proof is not proof for this mount. The existing imported-media 14-file history is not re-run or recertified here. One focused synthetic mount test checks gate-off identity, missing-witness closure, same-core ownership, native authorization, preview rejection before initialization, original initial lookup/delegation, and owned resource closure. It makes no TCP/SQL/S3 calls and does not prove provider upload behavior or enable HTTP in a deployed service.
